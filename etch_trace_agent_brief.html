01 / Why this agent

문제는 ‘이상 감지’ 이후에 있습니다.

이상이 감지되면 엔지니어는 여러 데이터와 문서를 오가며 원인을 탐색합니다. 우리는 그 과정에서 반복될 것으로 예상되는 조회·비교·근거 수집·보고서 초안 작성을 자동화 대상으로 봅니다.

ⓘ
검증 전 문제 가설입니다. 실제 반도체 팹의 평균 조사 시간이나 휴리스틱 의존 비율을 측정한 것은 아닙니다. 이 프로젝트는 공개 데이터로 조사 업무를 재현하고, 자동화 가능성을 시험합니다.
AS-IS · 가정한 업무 조사자가 직접 수행
  1. 01 이상 run의 조건·이력 확인 사람
  2. 02 비교 가능한 과거 run 탐색 사람
  3. 03 신호 차이 계산 및 시각화 사람
  4. 04 관련 문서 검색, 조사 결과 정리 사람

사람은 데이터를 찾고 정리하는 시간과 실제 현상을 판단하는 시간을 함께 사용하게 됩니다.

TO-BE · 제안 Agent가 조사 지원
  1. 01 대상과 조건 확인 Agent
  2. 02 비교 대상 자동 탐색 Tool
  3. 03 통계 분석 및 문서 근거 검색 Tool + RAG
  4. 04 근거 기반 보고서 작성 및 검토 Agent → 사람

Agent가 단순 반복 작업을 맡되, 원인 확정과 공정 변경은 자동으로 수행하지 않습니다.

PRINCIPLE 01숫자는 코드가 계산

LLM이 CSV를 읽고 수치를 추측하지 않습니다. 통계 함수의 결과를 근거로 표현합니다.

PRINCIPLE 02정보를 찾되, 원인을 단정하지 않음

관측 사실, 관련 후보, 미확인 가설을 구분합니다. 데이터가 부족하면 부족하다고 답합니다.

PRINCIPLE 03반복 조사는 Agent, 기록 확정은 사람

상태를 유지하면서 추가 조회하고, 승인 이후에만 최종 조사 기록을 저장합니다.

02 / Product boundary

우리는 ‘원인 판정 AI’를 만들지 않습니다.

3일 안에 구현하고 평가할 수 있는 부분을 명시적으로 제한합니다. 도메인 전문지식이 부족한 상태에서 실제 공정 판단을 대신하는 척하지 않습니다.

✓ 이번 MVP에 포함

  • ✓장비·run·recipe·step 등 분석 맥락 확인
  • ✓비교 가능한 참조 run 탐색
  • ✓결측률·변화량·기초 통계 비교
  • ✓공개 매뉴얼 또는 데이터 설명서 근거 검색
  • ✓추가 조사 / 재질문 / 보고서 작성 분기
  • ✓사람 승인 이후 조사 기록 저장

— 이번 MVP에서 제외

  • —식각 선택비 예측 또는 최적 레시피 추천
  • —원인에 대한 인과적 확정
  • —실제 장비 제어 및 공정 조건 변경
  • —실제 팹의 생산성 개선 효과 주장
  • —대규모 멀티 Agent·복잡한 인증 인프라
  • —고장 기록의 시점을 실제 고장 시작 시점으로 단정

04 / User journey

사용자가 요청하면 이렇게 동작합니다.

아래는 실측 분석 결과가 아니라, 기능을 설명하기 위한 가상 데모 시나리오입니다. 실제 데이터셋의 필드와 라벨에 따라 시연 내용은 조정합니다.

DEMO REQUEST · FICTIONAL
“장비 ET-02의 run-184가 이상해 보여요. 같은 레시피의 이전 run과 비교하고 조사 보고서를 만들어 주세요.”

사용자는 복잡한 SQL이나 분석 스크립트를 모르더라도 조사를 시작할 수 있습니다. 최종 판단은 사용자에게 남습니다.

01
조건 확인

실제 비교를 위해 같은 recipe뿐 아니라 step과 측정 시점을 확인합니다. 빠진 조건이 있다면 물어봅니다.

02
데이터 조회 + 계산

참조 run을 고르고 압력·유량 등의 가용한 신호를 비교합니다. 수치 계산과 데이터 검증은 Python 코드가 수행합니다.

03
문서 근거 검색

해당 신호의 정의·제약·의미를 데이터 사전과 공개 문서에서 찾습니다. 관련 근거가 없다면 불확실성을 남깁니다.

04
보고서 → 사람 승인

비교 사실, 가능한 추가 확인 사항, 모르는 부분을 정리합니다. 사용자가 검토한 후 기록합니다.

▤   최종 조사 보고서에 담길 내용

01 / FACTS어떤 조건을 비교했는가?선택한 run ID·recipe·step·통계 결과와 계산 기준
02 / EVIDENCE무슨 근거로 말하는가?분석 데이터 경로·문서 ID·미확인 정보
03 / NEXT ACTION무엇을 추가 확인해야 하는가?가능한 후속 조회와 사람의 판단이 필요한 지점

05 / Data strategy

공개 데이터로 검증하되, 한계를 숨기지 않습니다.

우선순위는 ‘반도체’라는 이름보다 분석 가능한 구조와 해석 가능한 필드입니다. 첫날 자료를 실제로 내려받아 열어본 뒤 어떤 주장을 할 수 있는지 결정합니다.

우선 검토PHM Society 2018 Data Challenge

이온 밀 식각 장비 관련 시계열·운영 맥락을 제공하는 공개 과제 자료. 장비·recipe·step 등 설명 가능한 항목이 있는지 확인하고, 소수 run부터 분석합니다.

주의: 데이터 접근·로딩을 첫날 확인해야 합니다. 원본 기록에 없는 물리 단위·정확한 고장 시작 시각·인과 관계를 만들어 내지 않습니다.
공식 데이터 설명서 ↗
대체 검토UCI SECOM

반도체 제조 측정 변수와 품질 판정 라벨로 구성된 데이터셋. 통계적 이상 조사 흐름은 시험할 수 있지만, 익명화된 특징을 실제 장비 변수처럼 해석해서는 안 됩니다.

주의: 이 경우 프로젝트 제목을 ‘제조 품질 데이터 조사 지원’으로 낮추고, 구체적인 식각 원인 분석은 주장하지 않습니다.

06 / Success criteria

성공은 ‘그럴듯한 답변’이 아니라
검증 가능한 조사 수행으로 측정합니다.

이상 원인에 대한 확정 정답 라벨이 없다면 ‘원인 진단 정확도’를 만들지 않습니다. 평가 가능한 수준을 명확히 나눕니다.

평가 축측정 방법비교 대상 및 주의사항
조회 정확성질문에 맞는 대상과 참조 구간을 선택했는지 정답 세트와 대조같은 recipe·step 필터를 사용하는 고정 로직과 비교
수치·근거 정합성보고서 수치와 Python 분석 결과의 일치, 문서 ID와 주장 간 대응 확인확인되지 않은 단위·원인 생성은 실패로 판정
예외 처리참조 데이터 없음·결측 과다·조건 누락·도구 실패 시 응답 평가모른다고 멈추거나 추가 질문하는 것도 올바른 행동
조사 과제 효율동일 난도의 과제에서 완료까지 걸린 시간·도구 호출·사용자 조작 수교육용 비교 결과이며 실제 팹 생산성 개선으로 해석하지 않음
승인 흐름수정 요청 반영·미승인 저장 시도 차단 여부 확인승인 이전 저장 0건이 목표 — 구현 테스트 기준

07 / Three-day build plan

3일 안에 작동하고, 설명하고, 평가하는 계획

프레임워크보다 데이터 검증을 먼저 수행합니다. 첫날에 성립하지 않는 가설을 발견하면 범위를 바꾸고, 그래프는 그대로 재사용하는 전략입니다.

DAY 01 / DATA FIRST

데이터·도구 준비

  • 원본 일부 다운로드·스키마 확인
  • 조사 과제 5~10개 정의
  • run 조회·비교 Python 함수 작성
  • 문서 인덱스 최소 구축
완료 기준: Agent 없이도 조사 1건 계산 가능
DAY 02 / GRAPH

Agent 흐름 구현

  • LangGraph StateGraph 연결
  • 다음 행동 판단·반복 상한 구현
  • RAG/분석 도구 호출
  • 사용자 재질문·승인 인터럽트
완료 기준: 결과를 근거와 함께 작성·승인 가능
DAY 03 / EVALUATION

실패 사례와 데모

  • 조건 누락·조회 실패 테스트
  • 계산·문서 출처 검증
  • 고정 흐름 대비 완료율 비교
  • 시연·성과·한계 발표 정리
완료 기준: 성공뿐 아니라 실패·미완료도 설명 가능
팀 구현 분담 예시: 데이터 파이프라인/검증 · LangGraph/도구 설계 · API/UI · 평가/발표. 팀 규모에 따라 겸임할 수 있습니다. MCP나 Spring Backend는 수업 요구사항에 따라 적용하되, 초기에는 인터페이스를 단순하게 유지합니다.
