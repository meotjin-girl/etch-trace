# SOP-ETCH-12 식각 장비 이상 대응

| 담당 팀 | 버전 | 최근 개정 |
| --- | --- | --- |
| Etch공정기술팀 | 1.0 | 2026-10-20 |

## 1. 목적 및 적용 범위

FDC 또는 SPC가 식각 설비 이상을 감지했을 때, 엔지니어가 장비 센서·recipe·과거 run·정비 이력을 대조해 의심 원인을 좁히는 절차를 정합니다. 계통별 점검 순서는 각 OCAP를 따르고, 이 문서는 모든 OCAP에 공통인 조사 흐름을 정합니다.

## 2. 용어

| 용어 | 뜻 |
| --- | --- |
| FDC | 장비 센서를 실시간 감시해 이상을 검출·분류하는 시스템 |
| SPC / OOC | 통계적 공정 관리 / 관리 한계 이탈 |
| OCAP | 이탈 신호(Activator)가 나면 순서대로 확인할 항목(Checkpoint)과 종결 조치(Terminator)를 정한 대응 계획 |
| 기준 run | 비교에 쓰는 정상 run. 선택 규칙은 §4.4 |
| 확인 가설 | 근거로 뒷받침되지만 현장 점검으로 확정되지 않은 원인 후보 |

## 3. 역할과 책임

| 역할 | 할 일 | 하지 않는 일 |
| --- | --- | --- |
| worker | 알람 인지, 장비·lot hold, 상태 전환, TRACE 접수, 재질문 응답 | 원인 판정, 조치 승인 |
| engineer | 조사, 원인 가설 판단, 조치 결정, 보고서 승인·수정 요청, 복귀 승인 | — |
| admin | 전체 조회, 문서 관리 | 보고서 검토·승인 |

## 4. 절차

### 4.1 감지와 격리

1. FDC 알람, SPC OOC, 후속 계측 이상 중 하나가 나면 이 절차를 시작합니다.
2. 인터락 abort는 재시작하지 않고, SPC 이탈은 현재 웨이퍼 처리 후 다음 lot 투입을 멈춥니다.
3. 영향 가능 lot은 SOP-ETCH-20에 따라 hold합니다.
4. 장비 상태를 Unscheduled downtime으로 바꿉니다 (SOP-ETCH-01 §4.2).
5. 아래 표로 해당 OCAP를 열고, TRACE에 장비·챔버·recipe·알람 코드·발생 시각·영향 lot을 접수합니다.

| 이탈 신호 | OCAP |
| --- | --- |
| 챔버 압력, throttle valve 위치 | OCAP-ETCH-PRS |
| 가스 유량 | OCAP-ETCH-GAS |
| 온도, He 후면 냉각, FlowCool | OCAP-ETCH-TMP |
| RF reflected power | OCAP-ETCH-RF |
| Endpoint 지연·미검출 | OCAP-ETCH-EPD |

### 4.2 Endpoint 지연 시 동시 비교

Endpoint가 기준 대비 10% 이상 지연되면 RF, 압력, 가스 유량 이력을 함께 비교한다.

- 기준은 §4.4로 고른 기준 run의 endpoint 시간 중앙값입니다.
- 5% 이상 10% 미만 지연은 주의로 기록하고, 같은 챔버에서 연속 3 run 반복되면 10% 지연과 같이 다룹니다.
- 함께 움직인 계통이 있으면 그 계통 OCAP를 먼저 엽니다. Endpoint 지연만 단독이면 OCAP-ETCH-EPD를 엽니다.

### 4.3 문제 범위 확인

1. 이상 시점 전후로 해당 챔버를 거친 lot·wafer를 MES에서 확인합니다.
2. 같은 recipe를 처리한 다른 챔버에도 같은 이상이 있는지 봅니다. 다른 챔버도 같으면 장비보다 공통 원인(가스 공급 설비, recipe 변경, 투입 웨이퍼)을 먼저 의심합니다.
3. 알람 이전 run에서 이미 센서가 움직이기 시작했는지 거꾸로 추적합니다. 알람·고장 기록 시각은 이상 시작 시각이 아닙니다.

핵심 질문: 이번 run만의 문제인가, 이전 run부터 시작됐는가?

### 4.4 같은 조건 비교

1. 같은 장비·챔버·recipe·recipe step의 대상 이전 run을 기준으로 씁니다.
2. 이상 기록 직전 24시간 안에 끝난 run은 빼고, PM 전 run과 PM 후 run을 섞지 않으며, seasoning·재인증 run은 뺍니다.
3. Step 시작 직후 과도 구간 2초는 비교에서 뺍니다.
4. 기준 run이 3건 미만이면 비교하지 않고 engineer에게 범위 확대를 묻습니다.

핵심 질문: 같은 조건에서만 비교해도 차이가 남는가? Recipe 변경이나 step 전환에 따른 정상 변화라면 장비 고장으로 보지 않습니다.

### 4.5 관련 센서 교차 확인

한 센서의 이탈만으로 원인을 정하지 않고, 각 가설이 다른 센서와도 맞는지 확인합니다.

| 가설 | 함께 확인할 신호 |
| --- | --- |
| 배기 계통 이상 | throttle valve 위치, 펌프 전류·속도, foreline 압력 |
| 가스 공급·제어 이상 | MFC readback, 공급 압력, 다른 가스 라인 |
| 압력 센서 이상 | 다른 압력계와의 차이, 영점 |
| 진공 누설 | 기저 압력, rate-of-rise |
| 냉각 계통 이상 | He 압력·유량, 챔버 압력 동반 여부 |
| RF 전달 이상 | reflected/forward 비, match 위치 |

압력 제어 장비에서는 압력이 설정값을 유지하더라도 throttle valve 위치가 먼저 변합니다. 압력값만 보지 말고 valve 위치를 함께 봅니다.

### 4.6 정비·변경 이력 대조

1. 최근 PM, 부품 교체, 챔버 세정, recipe·설정 변경 기록을 찾습니다.
2. 이상이 특정 작업 직후부터 나타났으면 그 작업을 조사 근거로 기록합니다.
3. 정비 이후 발생했다는 사실만으로 정비를 원인으로 단정하지 않습니다.

### 4.7 원인 후보와 점검 순서

1. 원인 후보를 확인 가설로 정리하고, 해당 OCAP의 Checkpoint 순서대로 점검합니다.
2. 장비를 열지 않는 점검(설정·이력·calibration 기록)을 먼저 하고, 장비를 여는 점검은 SOP-ETCH-01 §4.1 후에 합니다.
3. 조사 보고서는 FACTS(비교 조건과 계산 결과), EVIDENCE(근거 run ID와 문서 조항 ID), NEXT ACTION(추가 점검과 사람이 판단할 지점), UNKNOWN(확인하지 못한 것)으로 나눕니다.
4. 각 가설에는 근거 조항 ID를 최소 1개 붙이고, 없으면 "근거 문서 없음"이라고 씁니다.

### 4.8 검토·승인과 종결

1. engineer가 보고서를 승인해야 조치를 시작합니다. 수정 요청이 오면 반영 후 다시 승인받습니다.
2. 조치 후 OCAP의 Terminator 조건과 SOP-ETCH-01 §4.8 재인증을 통과하면 생산에 복귀합니다.
3. Hold lot은 SOP-ETCH-20에 따라 처분합니다.

### 4.9 에스컬레이션

| 조건 | 대상 |
| --- | --- |
| Unscheduled downtime 4시간 내 원인 가설을 못 좁힘 | 설비 파트장 |
| 재인증 2회 연속 실패 | 설비 파트장 + 장비 업체 |
| 같은 원인으로 30일 내 2회 재발 | 공정 기술 회의 |
| 가스 누출, 아크, 화재 감지 | 즉시 EHS. 현장 비상 절차가 이 문서보다 우선 |

## 5. 판정 기준·검증

- 편차는 기준 run 분포 대비 z-score로 표현합니다. |z| ≥ 3은 확인 필요 편차, 2 ≤ |z| < 3은 경미한 편차입니다.
- 기준 표준편차가 0에 가까우면 평균 차이(대상 평균 − 기준 평균)를 함께 적습니다.
- 수치에는 단위와 근거 run ID를 붙입니다. 표준화 값으로 수집되는 센서(이온 밀 FlowCool 등)는 물리 단위를 붙이지 않습니다.

## 6. 기록 관리

조사 기록에 아래를 남깁니다: 장비·챔버·recipe, 이상 run과 기준 run ID, 알람 코드·발생 시각·상태 전환 시각, 실행한 OCAP ID와 이상이 확인된 Checkpoint, 원인 분류, 조치, 조치 전후 값, 근거 조항 ID, 재인증 결과, 승인자. 승인된 기록만 조사 이력으로 저장합니다.
